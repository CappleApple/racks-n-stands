# Optional companions

## Curios

The sole class importing Curios is `compat.curios.InstalledCurios`. Its entry is guarded by `ModList` and the integration setting. Curios is compile-only and is not embedded in the JAR. Without it, the base mod loads, gear remains stored, and Curios-only filters reject new items unless another positive rule explicitly admits them.

The bridge uses **Curios 9.5.1 for Minecraft 1.21.1** `CuriosApi.getItemStackSlots(ItemStack, Level)`. It returns all compatible registered slot types using Curios validators. Fixtures accept an item when its compatible slot set intersects the configured set. Slot compatibility is not reduced to static tags. A failing addon validator is logged once per item and fails closed for Curios detection; generic displays remain usable.

**In this API version, slot identifiers are strings such as `ring`, `necklace`, or `sigil`.** Curios' slot JSON resource has a namespace, but the runtime slot identifier comes from its path. Do not write invented forms such as `curio:ring` or `artifacts:head` unless the installed API actually reports that exact identifier. Debug output shows the exact compatible strings.

Example profile filter:

```json
{"accepted_curio_slots": ["ring", "sigil"]}
```

A pack can define a custom slot at `data/mypack/curios/slots/sigil.json`, then accept `sigil`. Slot creation and item assignment belong to Curios. Racks N' Stands does not register accessory slots in the player's inventory.

Every stock non-armor display, including the six-slot Display Shelf, accepts any item without Curios. Curios slot restrictions are available only when a pack explicitly requests them through a filter. Retired accessory-specific IDs remain registered for existing worlds but are absent from recipes and the creative tab. Equipment swapping affects vanilla equipment slots, not the player's Curios inventory.

Curios rendering uses the normal stored ItemStack model. Normal Minecraft durability repairs through the shared engine; custom Curios charge or energy systems are untouched. The test datapack generated by `tools/prepare_curios_tests.py` assigns feathers, string, paper, and an iron sword to actual registered Curios slots solely for development tests.

## Rituals Not Rolls

The integration consists entirely of a pre-included Repairing datapack definition in the mod JAR:

```text
data/racksnstands/ritual_enchanting/enchantments/repairing.json
```

Rituals Not Rolls reads it through its normal datapack loader. There is no mod-presence check, version requirement, dependency declaration or load-order requirement. The definition contains: `enchantment`, `materials`, `levels`, `particle`, and `particle_color`. Four stable affinity identifiers (`iron_ingot`, `amethyst_shard`, `experience_bottle`, `echo_shard`) participate in RNR's normal knowledge and discovery flow. Levels I–X have increasing thresholds of 128 through 1280. RNR controls material delivery, power and knowledge; fixture construction materials still have no maintenance effect.

Override that exact path to change acquisition balance. To disable only the bundled integration, replace it with:

```json
{"enchantment": "racksnstands:repairing", "enabled": false}
```

RNR's data setting is authoritative; no competing Java configuration toggle is introduced. When RNR is absent its custom data directory is inert. The real Repairing enchantment and ordinary anvil/loot acquisition remain available.

## Rendering compatibility

Weapons and tools select the third-person right-hand model through the model's transform hook. Baked geometry is centered, retains its hand scale, and uses datapack orientation instead of the player's grip offset. Custom item renderers receive the hand context. Tridents use their native 3D model. General items keep normal fixed rendering, and packs can override `display_context` per item/tag.

Simply Swords' sword tag and Simply More's `weapon_types/all` tag select downward defaults. Axes, greataxes, hammers and pernachs receive upright defaults. Simply Swords' rotated 3D greathammers have separate rules, including optional exact IDs because its implicit family tags can be empty. These are ordinary bundled datapack files, with no mod-presence or version check.

Standard item glint is masked by the original atlas alpha, preventing transparent sprite areas from shimmering over neighboring items. Custom renderers retain their own texture/glint path. Armor uses baked humanoid parts, NeoForge armor-model/texture/tint/animation extensions, material layers, trim atlas sprites, and normal armor glint. Unsupported worn equipment falls back to its item model.

No ItemEntity, ArmorStand, fake player, or marker entity is created to render gear. The local player supplies armor extension context without changing their equipment. Addons whose renderers assume that entity is actually wearing the displayed armor may need display-aware support.
